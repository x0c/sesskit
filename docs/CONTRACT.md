# SessKit contract (v1)

## Envelope

Every CLI command prints one JSON object to stdout:

```json
{"ok": true, "data": {}, "error": null, "meta": {"version": 1}}
```

On failure `ok` is false, `data` is null, and `error` has `code`, `message`, `hint`, `next_commands`.

Exit codes: `0` ok, `1` error, `2` usage, `3` not found, `5` ambiguous.

## Schemas

| File | Purpose |
|---|---|
| `schemas/session.v1.json` (packaged as `sesskit/schemas/…`) | List/search session object |
| `schemas/conversation.v1.json` | Plain-text message in show/export |
| `schemas/transcript.v1.json` | Rich event in share (`schema` field = `sesskit.transcript/v1`) |

Root `schemas/` is the doc-facing copy; wheels also ship identical files under `src/sesskit/schemas/`. When changing a schema, update **both** locations in the same change.

Legacy share payloads from a host may carry that host's own schema id (e.g. `corral.share/v1`). Neutral readers accept only `sesskit.transcript/v1` (`transcript.accepted_schema_ids()` with no arguments); a host that must still read its historical payloads supplies its legacy ids via the host extension (`legacy_schema_ids`) and accepts the union.

## Public conversation load

- **Session-dict entry (CLI + library):** `sesskit.load_session_conversation(session)` / `RuntimeParser.load_conversation(session)`.
- **Parser modules stay path-based** (OpenCode: `db_path` + `session_id`). Do not pass a whole session dict into `parsers.*.load_conversation`.
- **Missing history is an error** for the SessKit CLI (`ConversationLoadError` → envelope `ok: false`). Do not disguise “file gone / unreadable” as a successful empty transcript.
- **Corral soft-fails** on the same adapter (`sesskit_bridge.load_runtime_conversation` returns `[]`) so the TUI never crashes on one bad file. Do not “unify” that into raising inside Corral.
- **Conversation is an activity projection (Stage F, 2026-09-30):** for `claude`, `codex`, `opencode`, `cursor`, and `pi`, adapters project `load_activity` snapshots through `sesskit.conversation_from_activity`; Kimi stays on its legacy parser by scope decision. Per-runtime `parsers.*.load_conversation` functions are retained as the path-based compatibility entry, not the interpretation source.
- **Unified error policy:** an assistant turn whose text only surfaces a native error is hidden from the default chat view and returned with `include_errors=True` (`sesskit show/export --include-errors`) on every runtime that marks such turns. Assistant text carrying error evidence alongside genuine reply content is always shown. Injected (non-human) user rows are skipped, mirroring the v1 projection.
- **Intended behavior changes vs the retired per-runtime interpretation** (real-history differential, 2026-09-30; live histories, counts are snapshots): error-only turns newly hidden by default (codex 81/200 sessions, opencode 26/200, claude 1/31; all restored with the flag); OpenCode v2 keeps native whitespace instead of stripping (23/200, cosmetic); OpenCode conversation follows native row order like the transcript instead of the legacy append-plus-timestamp re-sort (18/200); repeated identical error texts are preserved per turn instead of collapsed by text equality (6–11/200 across runs); same-text repeats separated by non-text rows are preserved per event instead of collapsed across message adjacency (1/200 codex); Pi `include_errors=True` does not resurface error text for turns whose error rides with tool/thinking parts (63/188 — still visible via `status_tag`, outcome, and `load_events`). Cursor is byte-equal (200/200 both modes); Pi default is equal (188/188); claude/codex flag-on restores every hidden turn (codex except the single repeat-collapse session above).
- **List previews and status tags are not projections:** `first/last_user_msg`, `last_agent_msg`, `status_tag`, and `completion_id` stay on the scanners' separate bounded-tail reads (scan speed; full-history loads would regress list timing). They are not derived from the activity snapshot.

## Listing modes

- Claude user prompts that begin with a rendered image marker such as `[Image #1]` and continue with human text are real sessions. Strip only leading image markers when choosing a fallback title; keep the original prompt in conversation/history. Do not classify that marker as a JSON-array title or drop the session from scan results. Reparse cached Claude metadata with this formerly rejected shape, so an unchanged history file recovers immediately after update. Corral needs the scanned history path to replace its hosted placeholder and populate Your prompts. Bracketed JSON/array fragments still remain low-value title candidates.
- Cursor sessions whose `store.db` is missing, unreadable, or contains no parseable message events can still have `prompt_history.json`. `load_events` must emit those prompts oldest-first as `user_message` events, matching `load_conversation`; do not append the fallback to a non-empty store event stream or duplicate users.
- Cursor sessions with no `meta.json` title and no `prompt_history.json` still list when `store.db` exists and holds at least one message blob (newer CLI `--print` one-shots write exactly this shape; verified 2026-09-30). The list path reads only the `meta`-table single row (store `name`, ignoring the generic `"New Agent"` placeholder) plus one blob-existence probe — never a blob scan. Such sessions list with `STATUS_NONE`, empty excerpts, and empty completion id; title and excerpts are backfilled by consumers from the preview conversation, never fabricated at list time.
- List `first_user_msg` / `last_user_msg` / `last_agent_msg` stay at most 300 characters. When the text is a host handoff wrapper, the host's extension transform extracts the inherited `Task:` line and the conversation digest **before** clipping; core clipping only truncates, otherwise the 300-char window is consumed by pickup boilerplate and title generation never sees the real request. Nested pickups flatten an earlier wrapper into `[Original request]` / `【原始需求】` on one line — peel inward (inner task wins) and drop leftover `You are picking up` on that line. Do not raise the raw slice to recover those bytes.
- **List excerpts must not go blank in long tool-heavy turns.** Claude reads a bounded tail (64 KB) for status; when that window holds no user or assistant text (only tool calls/results), backfill `last_user_msg` / `last_agent_msg` from a wider backward read (bounded). Status, `status_tag` and `completion_id` stay computed from the original window only — widening them would turn a mid-turn assistant sentence into a false `STATUS_DONE` and a false completion notification.
- Default scan drops sessions whose project `cwd` no longer exists (resume-oriented; **Corral must keep this default**).
- Pass `--include-missing-cwd` (or `include_missing_cwd=True` on scanners) for archive/search when history files still exist.
- Never turn `include_missing_cwd` on inside Corral’s recover / sidebar path.
- **Disposable automation workspaces never list.** A `cwd` is ephemeral when any path segment starts with a host-declared automation prefix (e.g. one automation family's `oc-manager-`, supplied via the host extension) **or** the `cwd` or any ancestor directory contains a `.sesskit-ignore` file. Scanners drop these sessions regardless of `include_missing_cwd`. The marker is opt-in: automation that launches real agent sessions may drop it in its workspace root when its sessions should stay out of listings; without it those sessions list normally. The owning automation may set `SESSKIT_INCLUDE_EPHEMERAL=1` in its own process to observe its sessions; never set it globally. Do not hide sessions by a temp-directory prefix alone: people also run real sessions from `/tmp`.
- Claude mid-turn human prompts are stored as `attachment` entries with `attachment.type == "queued_command"` (human `origin.kind` / `humanTurn`), not as `type == "user"` rows. Treat their `prompt` text as real user messages in `load_conversation`, `load_events`, and list tail state (`last_user_msg`), in file order; ignore the companion `queue-operation` rows so each prompt appears once. This is what populates Corral Your prompts when the user types while the agent is working.

## Export / share writes

- Refuse writing onto a session history path (or its symlink); see `sesskit.paths.assert_not_history_path`.
- Write JSON via same-directory temp file + `os.replace` (`atomic_write_json`). Do not truncate the destination in place.

## Runtime-specific restore semantics

- **Codex liveness:** use the shared process snapshot before inspecting open rollout files. On macOS, an executable with a long path can be missed by `pgrep -x codex` while its PID and open history file are present. A missing pgrep match alone is not evidence that the task ended.
- **Pi:** when reconstructing the active branch from a v2+ tree, start from the **last appended file entry**, then walk `parentId` (matches pi-mono `buildSessionPath`). Do not pick the leaf by max wall-clock timestamp — clock skew selects the wrong branch.
- **Cursor:** list-level `scan_signature` must **not** include `store.db-wal` (streaming writes would invalidate the whole list every few seconds). Per-session conversation / `extra_version` **must** still include the WAL so previews see uncheckpointed tails. Do not collapse these two version keys into one.
- **OpenCode:** list-level `scan_signature` must **not** embed `opencode.db-wal` mtime (streaming writes rewrite the WAL every few seconds without changing the list's session/message rows). Its per-database content fingerprint is read-only and hashes every row, in stable key order, of the list-driving `session`, `session_v2`, `message`, and `session_message` columns; counts and extrema alone are insufficient because tied/older timestamps and edits or deletions of non-maximum rows can change the selected list tail without changing aggregates. The live-process snapshot stays in the signature as before. The fingerprint uses a `mode=ro` connection with a short timeout and no explicit write transaction; busy/locked databases or schemas missing any tracked table fall back to file mtimes, conservatively allowing extra scans. Per-session conversation / `extra_version` and incremental row readers keep seeing WAL tails (never `immutable=1`). **Part-only writes are intentionally not fingerprinted** to avoid rescans for streaming churn; a part-only preview change may therefore remain cached until a tracked row or process change causes a rescan. This is a bounded freshness tradeoff, not a claim that every list-visible byte is covered. Live typed-v1 parity checks must select native session IDs and run both projections against one temporary snapshot made with `sqlite3.Connection.backup()` from a read-only source; sequential reads of a changing live database cannot establish parity ([Python API](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup), [SQLite Online Backup API](https://www.sqlite.org/backup.html)).

## Status tags and abnormal endings

List `status_tag` values come from `sesskit.titles` (`STATUS_DONE` / `STATUS_PENDING` / `STATUS_ABORTED` / `STATUS_NONE`). They are **history-tail inferences**, not liveness and not a substitute for Corral’s working/waiting/idle phase.

### Required semantics (product rule)

Consumers (Corral notifications, mobile “job finished”, scripts) must be able to tell **successful completion** apart from **abnormal ends**. Abnormal ends that exist in native history **must** be visible through SessKit — at minimum via correct `status_tag`, and ideally via retained detail (error text / code) in list fields and/or `load_events`.

| Outcome | Expected `status_tag` | Detail consumers need |
|---|---|---|
| Normal turn finished with assistant reply | `STATUS_DONE` | `last_agent_msg` / trailing `assistant_message` in `load_events` |
| Waiting on user | `STATUS_PENDING` | last turn is user-owned |
| Rate limit, quota, provider error, abort, interrupt | `STATUS_ABORTED` (or a future dedicated failure tag) | Human-readable error summary must not be dropped |
| Truly unknown | `STATUS_NONE` | Prefer unknown over false `DONE` |

**Do not** treat a native “task/turn complete” marker as success when the same record carries a non-empty error. **Do not** drop error-only assistant turns from `load_events` so that only the preceding user line remains.

### Native signals (reference)

Use these when implementing or reviewing parsers (not an event-bus API — SessKit stays pull/snapshot):

| Runtime | Success signal | Abnormal signal (examples) |
|---|---|---|
| Codex | `event_msg` / `task_complete` **without** `error` | Same event with `error` (e.g. `codex_error_info: usage_limit_exceeded`); `turn_aborted` |
| Pi | assistant `stopReason` in `{stop, …}` with content | `stopReason` in `{error, aborted, …}` plus `errorMessage` (e.g. weekly 429) |
| OpenCode | assistant `finish=stop`, no `error` | Non-empty message `error` → aborted (existing parser rule) |
| Cursor | Prefer transcript / store tail; list `status_tag` is weak today | Prefer unknown over false done when terminal reason is unclear |
| Claude | Stop / transcript end without interrupt markers | `system` entries with `error` (`formatted` human text + `status` HTTP code; 2.1+ live shape) → aborted; `[Request interrupted by user]` → aborted; final assistant text beginning `You've hit your session limit` → aborted |
| Kimi | Stable `step.end` / assistant tail | Cancel / failure markers in wire history |

### Verified gaps closed (2026-09-15 live Mac runs)

Previously confirmed failures, now covered by parser fixes + `tests/test_abnormal_endings.py` and re-checked on the original live history files:

1. **Codex usage limit:** `task_complete` + `error.usage_limit_exceeded` → `STATUS_ABORTED`; error message fills `last_agent_msg` / `load_events` when `last_agent_message` is null. Same path covers 401 / provider `other` errors (non-empty `error.message`).
2. **OpenCode provider/abort errors:** `message.error` (`APIError` with `data.message` + `statusCode`, `MessageAbortedError`) → `STATUS_ABORTED`; error text fills `last_agent_msg` / `load_conversation` / `load_events` even when the turn has zero text parts (previously the turn was user-only on mobile).
3. **Claude 2.1+ upstream errors:** `system`-type entries carrying `error.formatted` / `error.status` (401, ECONNRESET connection drops — reproduced live 2026-09-23 with a dummy key, no account needed) → `STATUS_ABORTED`; retry bursts collapse to one trailing assistant error; titles still use the real prompt, never the error text.
4. **Pi weekly rate limit:** `stopReason=error` + `errorMessage` → `STATUS_ABORTED`; error text retained in list fields and `load_events` (no longer user-only). Plain conversation hides error-only turns by default (chat view shows only real user/assistant text); pass `include_errors=True` (`sesskit show/export --include-errors`) to bring them back.
5. **Pi / OpenCode success paths** remain `STATUS_DONE` with the assistant reply.

Until consumers migrate, prefer `status_tag` + `last_agent_msg` together: do not treat `STATUS_DONE` alone as “notify job finished” without confirming the sample is not an older SessKit build.

## Completion identity (native-finality + metadata-invariant)

`completion_id` identifies one genuine native completion within a session. It is the notification dedupe key, so false stability (same id for distinct completions) and false churn (new id without a new completion) both cause user-visible harm — missed notifications or notification floods.

- **Strict native finality (Claude stop semantics):** a reply is terminal only on native end-of-turn evidence. Per the [Claude stop-reason reference](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons), `tool_use` means the turn continues executing — progress text followed by tool calls, or a tool-only tail after earlier assistant text, is mid-turn, never `STATUS_DONE`, even when assistant text is present in the tail window. Unresolved tool calls, retries, and truncation markers are likewise nonterminal. A real user reply may end a native turn; never invent a semantic task-completion classifier on top of text content.
- **Status and id share one bounded evidence read:** `status_tag` and `completion_id` are computed from the same bounded tail window (list-scan speed; no full-history load per scan). Excerpt backfill from a wider window must never widen the status/id window.
- **Metadata-invariant identity:** the id derives only from stable native completion/turn/message evidence (terminal record identity, turn/message ids, native stop/finish markers, final text hash) — never from file/DB aggregate `mtime`, byte size, titles, or queued/scheduling metadata. Metadata-only appends, touches, queue records, or title updates must not change the id of an unchanged completion. Identical answer text in different genuine turns must still yield different ids (the turn/message anchor differs). When no exact final anchor is available, return an empty id (`unknown`) rather than fabricating success; Corral treats empty-id `DONE` as non-notifiable.
- **Window-stable identity inputs (2026-10-01 acceptance rejection):** changing availability of user/list excerpts within a rolling scan window must never change the id of the same native final event. Both the anchor AND the tail material hashed into `completion_id` must be deterministic functions of the anchored terminal evidence (the terminal record/message identity plus its own text) — never of whether an excerpt happens to sit inside the bounded tail. Verified failure on installed 0.2.3: a Claude history (20 KB user text + final assistant event `a-final`, `stop_reason=end_turn`) parsed `STATUS_DONE`; after 90 metadata rows pushed the user text out of the 64 KB tail, the rescan was still `STATUS_DONE` with the identical terminal event and text, but `completion_id` changed and the consumer sent two pushes for one genuine completion. The stable-anchor guarantee therefore covers arbitrary metadata appends and window-boundary shifts, not only tiny appended rows. Display excerpts (`last_user_msg` wider-window backfill and friends) may keep using wider reads; identity inputs may not.
- **Same rule in every runtime adapter:** when fixing one adapter's id source, audit all six for the same aggregate-mtime/size/metadata pattern and correct each in scope. Abnormal endings keep their own identity path (`STATUS_ABORTED` with retained error evidence); waiting, device preferences, and per-device receipt dedupe are consumer-side and unchanged.

## Cross-runtime model evolution contract

This contract governs additive refactoring of sessions, plain conversations, rich activity events, errors, and tool calls. It does not authorize changing the v1 JSON schemas or Corral/iOS wire behavior as the first step.

### Ownership and outcome semantics

- SessKit owns historical session identity and metadata, raw-format interpretation and incremental history reads for all six runtimes, plus normalized conversation and activity evidence. Corral owns hosting, current process liveness, attention, and the phone-facing message/transport projection; it must not maintain a second raw-history parser.
- Historical outcome is separate from live phase. Keep the outcome distinction `done`, `pending`, `aborted`, and `unknown`; it describes history-tail evidence, not whether a process is currently running. Uncertain evidence must remain `unknown`, never default to success. Existing `status_tag` remains a compatibility projection during migration.
- A structured agent error is distinct from assistant-authored text. Its additive representation has `kind`, optional `code`, human-readable `message`, and `evidence`. `kind` identifies the broad failure class; `code` is populated only when native history provides one; `evidence` identifies the native record or explicit inference that supports the error. Do not manufacture native codes. Existing v1 text and status fields remain available and retain their current meanings for old consumers.
- Tool calls and results retain their correlation identifier when native history provides one. A result outcome is `ok`, `error`, or `unknown`; record whether that outcome is native or inferred. Missing or ambiguous evidence stays `unknown` and must not be silently represented as `ok`.
- A normalized activity event may carry `message_id` to identify one native message within a session. Events with the same `message_id` preserve the native part order. This identifier is not a cross-session identity. The Pi projection uses this grouping when one native message contains multiple parts.
- Loading distinguishes an available, valid empty history from history that is missing, unreadable, or unsupported. Preserve the legacy list-returning APIs as compatibility adapters while introducing any richer load result additively. Corral continues to soft-fail missing history to an empty conversation.

### Capability inventory and evidence boundary

The normalized model should be able to represent the union of capabilities encountered across runtimes: session create/resume/fork/compaction; message text, thinking, and media; tool calls/results, progress, and background work; structured questions, permission and plan approval, and MCP elicitation; child-agent work; turn/session outcomes and failures; and session metadata. This is a modeling inventory, not a claim that every runtime, version, host, or persisted format supports every capability.

Current documentation illustrates different surfaces: [Codex App Server](https://developers.openai.com/codex/app-server) documents `ThreadItem`, thread lifecycle/fork/compaction, runtime status, approvals, and elicitation; [Cursor CLI ACP](https://prod.cursor.com/docs/cli/acp) documents question, plan approval, todo, subagent, and permission requests; [Kimi sessions](https://github.com/MoonshotAI/kimi-code/blob/main/docs/en/guides/sessions.md) and [tools](https://github.com/MoonshotAI/kimi-code/blob/main/docs/en/reference/tools.md) cover persisted/resumable sessions, tool/media, and background work; [OpenCode v2 tools](https://opencode.ai/v2/docs/tools/) document questions, subagents, and background execution; [Pi session format](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/session-format.md) documents persisted message trees, branches, compaction, and metadata; [Claude tools reference](https://code.claude.com/docs/en/tools-reference) documents available tool and interaction surfaces, not the raw history schema. Apart from sources that explicitly describe persisted sessions (Kimi and Pi), these references do not establish raw-history formats; those mappings remain unverified. The sources are not a shared persistence contract. Adapters report only capabilities supported by observed native evidence; unobserved or unverified capabilities remain `unknown`, not `false`.

Stage G normalizes four of these behind capability flags (`subagent_linkage`, `usage_data`, `compaction_markers`, `message_origin`; Kimi deferred): `SessionRelation` via `session_relations()` (fork needs fork fields, bare parents stay `unknown`, Claude forward pointers yield `continuation`), per-message/turn `Usage` with native evidence only, `compaction` boundaries (standalone typed events only for never-projected rows; otherwise a `CompactionInfo` marker on the projected event), and `origin` (human/injected/system/unknown) on user-message events. v1 projection skips typed-only rows and renumbers densely, keeping bytes identical.

Each runtime exposes one adapter (`src/sesskit/adapters/`, `get_adapter` / `list_adapters`): `id`, `display_name`, frozen `Capabilities`, `scan`, `load_conversation`, `load_activity`, `load_events`, `open_reader`, and `signature`. Public entry points (`load_session_conversation`, `load_activity`, `load_events`, `RuntimeParser`, CLI) dispatch through the adapter registry only. Truthful declarations as implemented: incremental reading covers Pi (JSONL tree), Claude and Codex (JSONL byte offsets), plus Cursor and OpenCode (SQLite row cursors); typed activity covers all runtimes except Kimi (deferred); structured questions are normalized for Claude, Codex, Cursor, and OpenCode; native tool-result status holds for Pi, Claude, and OpenCode; explicit native turn markers drive outcome inference except on Cursor and Kimi (tail-role only); permission records, subagent linkage, and usage data are unexposed everywhere; the `include_errors` conversation flag is declared by every typed-activity runtime (loader support is Pi-first, widening with the activity-projection work).

### Structured interaction requests

The following are confirmed by current runtime documentation, not claims about what every installed version persists in native history:

- Claude documents `AskUserQuestion` as a multiple-choice request with an `Other`/notes path; questions remain open by default, while a configured timeout can close the dialog. [Tools reference](https://code.claude.com/docs/en/tools-reference)
- Codex App Server documents experimental `tool/requestUserInput` for user input, but the same mechanism can request approval for side-effecting MCP app calls with Accept/Decline/Cancel. It separately documents `item/permissions/requestApproval` and `mcpServer/elicitation/request` for form or URL elicitation. `serverRequest/resolved` may mean answered or cleared during turn cleanup, so the notification alone does not prove an answer. [App Server](https://developers.openai.com/codex/app-server)
- OpenCode v2 documents a `question` tool with grouped questions, multi-select, free-text answers, and dismissal as cancellation. Keep its permission action separate from question outcomes. [Tools](https://opencode.ai/v2/docs/tools/)
- Kimi documents `AskUserQuestion` with option selection, optional multi-select, free-form input, and background execution that returns a task id and later delivers the answer. [Tools reference](https://github.com/MoonshotAI/kimi-code/blob/main/docs/en/reference/tools.md)
- Cursor documents two distinct surfaces: CLI ACP `cursor/ask_question` is a blocking multiple-choice request with a `toolCallId`, grouped questions, and optional multi-select; the Agent overview describes asynchronous clarification while the agent continues other work. These are separate interaction paths, and the cited docs do not establish the native history format. [CLI ACP](https://prod.cursor.com/docs/cli/acp), [Agent overview](https://cursor.com/docs/agent/overview)
- Pi extensions can supply dialogs and custom UI; the example `question` tool records a selected/custom answer or cancellation. This is extension-provided behavior, not a guaranteed built-in request in every Pi session or host mode. [Extensions](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md), [question example](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/question.ts)

These facts motivate, but do not prove native persistence for, a normalized interaction model. Classify by request purpose and associated item/approval evidence, never by tool name or protocol method alone. Keep user questions, permission approvals, and MCP form/URL elicitation distinct; ordinary natural-language questions remain conversation text. Preserve a call id when present; represent grouped questions, option choices, free-text answers, and multi-select capability without flattening their structure. Track question resolution as `pending`, `answered`, `dismissed`, `expired`, or `unknown`, and retain asynchronous answers against the original request. A resolution/cleanup notice alone is not an answer. Use `pending` only when native evidence explicitly shows an unresolved request; a missing tool result alone is insufficient and must remain `unknown`. Until a runtime's native history shape is verified, mark its parse capability as unknown rather than inferring fields from its UI or protocol documentation.

### Current implementation and verified gaps

This is the implementation baseline, not the target contract above:

- Transcript v1 (`src/sesskit/transcript.py`) exposes only `user_message`, `assistant_message`, `thinking`, `tool_call`, and `tool_result`. `load_activity` (`src/sesskit/activity.py`) is the single raw-history interpretation source for the migrated runtimes (**Pi, Claude, and Codex**): it returns an `ActivitySnapshot` (`available`/`empty`/`unavailable`, never a bare `[]`), typed `ActivityEvent`s with native evidence and session-local `message_id` grouping, `ToolResultOutcome` with native-vs-inferred evidence (an evidence-free result stays `unknown` in the typed layer), structured `AgentError` on error-only turns alongside the legacy assistant text, a tail `SessionOutcome`, and `to_v1_dicts` projection. `load_events` for Pi/Claude/Codex is now generated from that snapshot (verified byte-identical to the retired duplicated parsers on 47/47 real Claude and 199/199 real Codex histories plus fixtures); the other three runtimes keep their dedicated transcript parsers and report `unsupported` from `load_activity`. Full-snapshot `ActivitySnapshot.cursor` stays `None` (never inferred from mtime); incremental reads use the separate `open_activity_reader` protocol below. `load_events` serialization is unchanged. The **Claude** branch normalizes `AskUserQuestion` inputs to grouped `InteractionRequest` questions (prompt/title/options/multi-select; free-text `Other` path per docs), answers link only for single-question calls with a non-error string result, resolution is `answered` only on such results (missing/failed results stay `unknown`, never `pending`), and the tail `SessionOutcome` mirrors the Claude `status_tag` rules (upstream system error with native `error.status` code, user interrupt, session-limit prefix, user-tail pending, assistant-tail done). Verified by fixtures plus v1 parity over recent real Claude histories (a re-scan found 12 `AskUserQuestion` calls across 6 of 47 sessions, all with results; multi-question and `multiSelect` variants present). Two evidence corrections landed after that baseline: (1) a missing `is_error` key on Claude tool results is **not** native success — real answered `AskUserQuestion` results omit the key entirely (11/12 sampled; only the rejected one sets `is_error: True`), so the typed layer records explicit booleans as `native`, empty outputs as `unknown`, and non-empty outputs via the text heuristic as `inferred` (v1 projection stays `"ok"`); (2) tool calls without matching results are not completion — Pi and Claude tails with unmatched calls report `unknown` instead of `done` (17/187 real Pi sessions move from list-level done to typed `unknown`; one pre-existing list-aborted/activity-done divergence on `3794e1f8` is unrelated and still open). Pure tool-call turns count as assistant-side tail so the outcome cannot fall back to an earlier user text.
- Claude mid-turn `attachment`/`queued_command` prompts are real user messages **only with explicit human evidence** (`origin.kind` in `human`/`user`, or `humanTurn: true`). Hook-injected `<task-notification>` blocks reuse the same channel — 18 with `origin.kind: task-notification`, 8 with no origin at all, versus 51 genuine human prompts — so a missing origin must never default to human, and the notification shape is excluded as defense in depth. `load_conversation`, `load_events`, and list tail state all share `queued_command_text`, so the rule applies once.
- The **Codex** branch mirrors `_parse_codex` emission (user/assistant dedup, reasoning, function/custom calls, heuristic outputs, `task_complete` fallback to error text) and the list tail rules (`turn_aborted`/`task_complete`+error → aborted with native code; user tail → pending; `task_complete`/assistant text → done; else unknown; unmatched calls in the terminal turn downgrade done → unknown). ### Typed activity and incremental reader API (additive)

These additive contracts do not change transcript v1 or require every runtime to supply every field:

- `ActivitySnapshot`: `state` is `available`, `empty`, `unavailable`, or `unsupported`; include `events`, a `SessionOutcome` (use `unknown` with unknown evidence when history gives no outcome), and optional opaque `cursor` and `generation`. `empty` means a supported, readable history with zero normalized events; `unavailable` means expected history could not be read; `unsupported` means this parser cannot interpret the format. `cursor` is only a resume position when that runtime provides a safe incremental boundary; `generation` identifies the source version when available. Never infer a cursor from a file timestamp alone. Keep `load_events(session) -> list[dict]` behavior and serialization unchanged as the v1 compatibility projection.
- Incremental reads use the separate `open_activity_reader(session, cursor=None)` API. A supported reader's `poll()` returns typed events, `reset`, a `generation`, and a new opaque cursor; unsupported runtimes report `unsupported` so consumers can fall back to `load_activity()`. `page(before=None, limit=...)` returns an older page of typed events, an opaque next `before` token, and `has_more`. The cursor and page token are JSON-safe, versioned, self-validating values; callers persist and return them without interpreting their contents. A reset means the returned events replace the previous generation, not append to it. This protocol is separate from `ActivitySnapshot.cursor`, which remains `None` for the full-snapshot `load_activity()` API.
- `ActivityEvent`: retain ordered `seq`, optional `ts` and session-local `message_id`, event `type`, and `Evidence`. For tool events preserve native tool name, call id, raw arguments/input, and raw output/result when present; attach optional `ToolResultOutcome` and `AgentError` independently of assistant-authored text. Keep these optional/raw fields additive so parsers do not fabricate structure or discard unfamiliar native payloads. A missing result status is `unknown`, never an implicit `ok`.
- `InteractionRequest`: optional on an event and independently typed, with `purpose`=`question`/`permission`/`plan_approval`/`elicitation`/`unknown`; optional request id and tool call id; ordered question groups/items with optional prompt, title, options, multi-select/free-text capability; optional answer records linked to their question; `resolution`=`pending`/`answered`/`dismissed`/`expired`/`unknown`; and evidence for purpose and resolution. Preserve native item/call linkage where present. Classify by request content and surrounding approval/item evidence, not a tool name or method alone: Codex `tool/requestUserInput` may be either user input or MCP side-effect approval, so absent discriminating evidence its purpose remains `unknown`. A missing tool result alone never makes resolution `pending`.

Each typed field that a runtime cannot provide stays absent or `unknown` with evidence; partial question structure and raw native payloads are valid. The Pi reader uses the file's native tree: it advances only when file identity, size, the saved boundary checksum, and the appended `parentId` chain continue from the known leaf. A no-change poll checks file metadata without reading or parsing history; incomplete trailing lines wait for a newline. A branch switch, truncation, replacement, or invalid cursor creates a new generation and returns only the reconstructed active branch. Incremental event `seq` values remain stable within a generation, and native entry IDs remain the `message_id` grouping key. Pi event normalization is shared with `load_activity()`; v1 event bytes stay unchanged. Kimi behavior is unchanged.

The Cursor and OpenCode readers use SQLite row cursors over read-only connections that keep WAL-visible tails (never `immutable=1`): the cursor holds an opaque versioned fingerprint (file identity plus WAL state plus a SQLite `data_version`), the last committed row position (`rowid` window for Cursor blobs; per-session `(time_created, id)` / `(seq, id)` ordering keys for OpenCode v1/v2), the boundary-row checksum plus event count, and compact interpreter aux state (pending tool results/calls, emitted call ids, open-turn tail flags, with bounded overflow) so a resumed reader continues the same row-sequence interpretation. A no-change poll stats the main file and its `-wal` sidecar only and never opens the database. An append poll reads only rows after the committed row position (plus a bounded recheck window over the trailing rows to catch in-place content updates via a cheap per-row length/checksum signature); it never re-reads or rebuilds the whole per-store/per-session window. Appends are accepted only when the fingerprint continues and the recheck window still matches the cached boundary; a vacuum, rowid reuse, checkpoint reshuffle that moves the boundary, in-place edit inside the recheck window that changes interpreted events, file replacement, or invalid cursor starts a new generation with a full bounded re-read whose events replace the prior generation — reset only on such evidence, never speculatively. Deltas feed the same row-sequence builders as `load_activity()` (no second interpreter) with carried state, so `seq` stays stable within a generation and `to_v1_dicts` parity holds; `page(before, limit)` walks the current generation backward with an opaque token, preserving call/result pairing across page edges. Local measurement after the change (2026-09-30, temp copies, counts only): largest Cursor store (134 MB, 952 JSON blobs → 1500 events) append poll ~0.7–0.8 ms fetching 1 row (was ~186 ms rebuilding 952 rows), no-change poll ~0.02 ms; largest OpenCode v2 session (396 rows → 1172 events) append ~1.0 ms fetching 1 row (was ~31 ms), largest v1 session (370 messages / 1353 parts → 855 events) append ~1.0 ms fetching 1 row, no-change ~0.05 ms stat-only. The Cursor reader additionally shares exactly the snapshot's `prompt_history.json` fallback through one code path (empty store rows fall back to prompts oldest-first, never appended to a non-empty store stream): its fingerprint also carries the prompt-file stat plus prompt event count and boundary, a no-change poll stats the prompt file alongside the main file and `-wal` sidecar, a prompt append extends the generation without reset, and store rows appearing later switch from fallback to store with a new generation.

The Claude and Codex readers use JSONL byte-offset cursors over the same row-sequence builders as `load_activity()` (no second interpreter). The cursor is opaque, versioned, and JSON-safe, carrying a content fingerprint (head checksum over a frozen prefix length plus device/inode identity, never inode alone), the committed byte offset of the next unread complete line, the boundary-line checksum, the materialized event total, and compact interpreter aux state (Claude: pending upstream error; Codex: open native turn; both: dedup tail hash, unresolved call ids with bounded overflow, outcome summary). A half-written trailing line is never consumed. A no-change poll stats the file only and parses nothing; a same-size newer-mtime poll re-verifies head plus boundary with two bounded reads before reporting no change. Truncation, replacement, fingerprint mismatch, or a corrupt/foreign/old cursor rebuilds with `reset=true` and a new generation, never continuing silently. Cold open builds the full interpretation in one pass but returns only a tail window (default last 200 events, caller-tunable), keeping the response bounded while `seq` stays snapshot-global: the window always equals the matching suffix of the snapshot with identical seq, content, and pairing. (Local measurement: the largest histories, 91 MB Codex / 63 MB Claude, are dominated by a few huge tool-output lines and parse in ~0.15 s into hundreds of events, so one full build per open is cheap while steady-state polls parse only appended bytes; parsed rows are freed after each build.) `page(before, limit)` slices the materialized generation with opaque `before` tokens, so backward pages reassembled always equal the full snapshot and pairing is global: a tool call and its result on different pages still pair by `call_id`, and the call event carries the resolved interaction wherever the result row has materialized. Reader outcome always equals the snapshot outcome function over the same materialized bytes, and turns derive identically. Two documented stream-vs-snapshot edges: a trailing upstream error (Claude) is emitted optimistically at poll end — if the agent later recovers with reply text the delivered stream keeps both while a later snapshot shows only the text; and linkage that arrives late (a result/usage/verified row after its call/message event was already delivered) enriches only the materialized list, never re-emitted polls — consumers join call/result by `call_id` exactly like the v1 pairing rule. The v1 projection of the materialized window is field-for-field compatible with `load_events`. Opening with a cursor validates the fingerprint without a full parse while the file is unchanged (full materialization is deferred to the next change or page); a grown file rebuilds with `reset=true` like the Pi reader. Kimi behavior is unchanged.

### Compatibility and migration gates

Keep the current v1 schemas and Corral behavior working throughout the additive migration. Preserve bounded mobile tail/page behavior; do not change the iOS wire format in the first step. Root and packaged v1 schemas remain byte-identical unless a separately reviewed schema-version change is made.

Use this migration order, starting with Pi as the pilot runtime:

1. Integrate the typed outcome, error, and tool-result models already present (done for Pi, Claude, Codex; remaining runtimes follow the same additive pattern); design any load-state/cursor API additively without changing v1 serialization.
2. Adapt the six runtime parsers to those models while retaining native evidence and keeping plain conversation separate from rich activity; add structured interaction and incremental-load support only where native evidence supports it.
3. Add compatibility projections for existing session dictionaries, `ConversationMessage`, transcript v1, and Corral's existing wire behavior; migrate one consumer at a time only after parity is shown.
4. Consider a new external schema or iOS wire version only in a separate compatibility review after all current consumers are accounted for.

Before each migration slice is accepted, verify the six supported runtimes (`claude`, `codex`, `opencode`, `kimi`, `cursor`, `pi`) against these cases where native history permits: normal completion, pending user turn, aborted/error ending, unknown or incomplete tail, tool call/result success, tool call/result error, missing correlation or status evidence, valid empty history, and unavailable history. Assert that native evidence is distinguished from inference, the new typed model distinguishes structured errors from assistant-authored text while the legacy v1 projection remains unchanged, unknown never becomes success, legacy payloads remain equivalent, and Corral still soft-fails missing history and respects bounded mobile reads. Measure cold full-history load and warm incremental-tail load for each migrated runtime; preserve bounded tail/page reads and establish a per-runtime latency and memory baseline before extending the migration beyond the Pi pilot. For parser or load-wiring changes, also follow the live-runtime checks below.

Rollback is additive: disable the new typed-model adapter and return to the existing v1 projections while retaining source history. Do not roll back by deleting or rewriting history, silently changing v1 fields, or leaving Corral pointed at a partially migrated representation.

OpenTelemetry GenAI event conventions are a design influence for naming and separating evidence only ([agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md), [general events](https://opentelemetry.io/docs/specs/semconv/general/events/)). SessKit does not copy or adopt the telemetry schema; its models remain focused on durable native session history and compatibility with current consumers.

Release compatibility: `0.2.1` is the minimum artifact version for consumers relying on thinking-only Pi error lifecycle events and the added incremental readers. Installing the published `0.2.0` artifact does not provide those later fixes. ## Verification (mandatory when changing parsers or load wiring)

### Conformance verifier contract

`sesskit verify` is an internal-consistency check across SessKit's own views, not an independent semantic oracle for what an agent said or whether its outcome is correct. Keep the v1 envelope and event schema unchanged; additive report fields are compatible.

- A scan, conversation load, activity/event load, supported reader, or applicable reader probe error is a verification failure and must prevent `passed: true`. Do not turn exceptions into empty successful views or hide `load_failed` / `unavailable` counts. An actually absent runtime history is a skipped/unverified sample, distinct from a failed read of history the scan claims exists. A scan yielding no samples is explicitly unverified/skipped, never a verified pass.
- Kimi's lack of typed activity and incremental-reader support is an expected capability boundary. Its legacy conversation and v1 event checks remain applicable and must run; the unsupported typed/reader paths are not failures. For runtimes that declare support, an unavailable snapshot or failed reader is a failure.
- Compare normalized events by their complete content, not only sequence and type: include text, timestamps, message/turn and tool-call correlation, tool names and raw input/output, result status/evidence, structured question and answer linkage, errors, and outcome. A cold incremental-reader result may be either the exact full snapshot or an exact suffix window with the same global sequence numbers. Reassembled pages must equal the full snapshot, including all normalized fields and outcome. Do not accept renumbered or content-altered events.
- Conversation/event consistency must catch missing and empty role projections even when either side has no matching rows. Respect the shared intentional-visibility rules: only content intentionally hidden from one projection is excluded; an empty opposite view is not itself proof that all content was intentionally hidden.
- For typed-activity runtimes, compare conversation turns to the exact ordered `(role, text)` projection selected by the shared visibility predicate; do not accept arbitrary substring matches, duplicates, omissions, or reordering. Kimi remains on its legacy reader, which groups assistant text chunks within a user-delimited span with `\n\n`; its v1 comparison must preserve that documented grouping rather than invent typed support.
- Independent reads can observe live history changing. Use stable source evidence to compare views, or report the comparison as inconclusive; an inconclusive comparison cannot support `passed: true`. Do not turn a changing source into a false failure or treat it as a pass. Verification must never write to live history.
- Reader-probe exceptions and failed probe checks are failures when that probe is applicable. A probe that cannot be run because its source history is absent is unverified/skipped, not passed. Reports remain content- and path-free.
- `sesskit verify --sample N` accepts nonnegative limits: `0` performs no scan and reports the selected runtimes as unverified; a negative value is a usage error. Never coerce zero to the default sample or to one session.

Unit tests that **mock** `load_conversation` can stay green while the real registry wiring is broken. After any change to parsers, registry adapters, transcript parsing, status inference, or CLI show/export/share:

1. Run the fixture wiring tests (`tests/test_registry_load.py`) — they must exercise the **real** adapter, not a session-dict stub that hides path wiring.
2. Run the shared conformance suite (`tests/test_conformance.py`) — every runtime adapter passes the same invariants on synthetic fixtures (seq order, tool pairing, evidence, unknown-stays-unknown, v1 parity, conversation consistency; Kimi on v1/load paths only).
3. On a machine with local history, run `sesskit verify` (options `--runtime` repeatable, `--sample N`, `--json`) as the required real-history consistency gate instead of ad-hoc scripts. It reports load success/failure counts, typed-vs-v1 parity, invariant violations, event-type/evidence/outcome distributions, median/p95 timings for scan, snapshot load, and incremental reader open/poll, plus per-runtime largest-history reader timings (cold open, no-change poll, backward page, append poll with append-vs-snapshot-suffix parity on a temp copy — never mutating history) — counts and timings only, never content or paths. Scan/load/event/reader/probe failures prevent `passed: true`; runtimes with no samples are explicitly unverified/skipped and also prevent an overall pass. Kimi's unsupported typed activity and reader paths are expected; its legacy checks still run. Parity is internal consistency, not an independent semantic oracle.
   - `load_session_conversation` / registry load succeeds (no `TypeError` from passing a dict as a path).
   - Roles are only `user` / `assistant`; no empty text; no literal `"None"`.
   - Strong system / injection markers must not appear in plain user turns (e.g. `system reminder`, `<system`, `task-notification`, `<ide_opened_file`, `<agent_skills>`, `<mcp_file_system>`, `<function_calls>`).
   - Every plain user text appears in `load_events` `user_message` texts (allow substring match when share splits more finely).
4. **Fine-grained live runtime checks (required for SessKit maintenance, not optional polish):**
   - Prefer **fresh one-shot prompts** per installed runtime (install the CLI if missing; skip only when policy forbids install — e.g. removed Claude Code — or when auth/quota truly blocks, and record the skip).
   - For each runtime, verify **at least one success path** and, when reproducible, **one abnormal path** (usage limit, rate limit, forced error). Compare **native history** → SessKit `status_tag` / `last_agent_msg` / `load_events` on the **exact** session path (do not trust “matched N of scan window” without path/id equality).
   - Official docs / web search inform expected native fields; they do **not** replace a live run on this machine.
   - Hooks / notify / SSE are Corral integration concerns; SessKit verification still owns correct **parse of whatever landed on disk** after those runs.
5. If Corral consumes the same change: confirm Corral’s `sesskit_bridge` path and SessKit registry path return the **same** `(role, text)` sequences for the sampled sessions.
6. Do not claim “data correctness OK” from fixture-only runs when real history is available. Do not claim “abnormal endings OK” without a live failure sample (or a checked-in fixture cloned from one).
7. **No armchair modeling.** Every parser or inference change must be confronted with that runtime's real history files before merge: report sampled session counts, event-type totals, and the exact evidence behind each new rule (e.g. all 11 answered Claude questions omit `is_error`; hook `<task-notification>` reuses the `queued_command` channel with non-human or missing origin). When replacing a parser with a projection of the new model, prove byte-identical output on real histories first (47/47 Claude files on 2026-09-29), then delete the old code — never the reverse. Missing native evidence (a flag, an origin, a result) must stay `unknown`/excluded, never default to the convenient reading. Skipped live runs must name the blocker: on 2026-09-29 fresh one-shot probes were blocked by Claude session limit (`You've hit your session limit`) and Pi insufficient credits (`BAD_REQUEST`), so the changed runtimes were verified by real-history parity plus fixtures instead; codex/cursor/opencode/kimi parsers were untouched and covered by 20-session real-history conversation/event sampling each (kimi: zero local sessions, unverifiable).
